# Channel experiments

Append-only measurement record. A channel entry is a unique repository path that is not
intentionally linked from standard project navigation and is used by one declared route. It is
still public, indexable, directly discoverable, and neither hidden nor attribution-proof.
Repository totals, referrers, and ordinary README traffic are not qualified views. GitHub Traffic
cannot prove identity, buyer intent, or uniqueness, so a view is never called a person, lead, or
customer.

### Frozen activation design

The pre-release is the only intentional direct link to the entry page; topics are classification
metadata and entry-page views are not attributed exclusively to the release. It will target the
exact merge commit and contain no uploaded asset, mention, discussion post, price, checkout, or
request for private input. GitHub-generated source archives remain available for the tagged
repository tree. Topics are limited to adding these accurate classifications: `ai-evaluation`, `llm-evaluation`,
`customer-support`, `support-automation`, `software-testing`, and `python`; existing accurate
repository topics remain. The repository description will be corrected once to name both active
open-source-impact and support-agent-evaluation work. No issue, pull request, comment, direct
message, scraped contact, or post in another person's project is an allowed distribution route. The release-body template is
versioned as `channels/github-native-v0.1.0-release.md`; publication replaces only
`{{MERGE_SHA}}` with the exact target commit. Views of the template source are not qualified views.

Immediately before publication, re-check and record the authenticated user-owned account, current
sponsor authorization, AI/project disclosure, exact copy, exact topic additions, and platform
state. A new identity, terms, recovery, or credential prompt stops for the human owner. After
publication, append the activation UTC timestamp, end timestamp, merge SHA, release URL, entry URL,
release-copy SHA-256, issue-form SHA-256, description before/after, topics before/after, and
owner-preview count. Freeze the default-branch issue form with the experiment; any form change
requires privacy/measurement review and a restarted window. On UTC days 1, 7, 13, and after the next daily refresh following day 14,
record the exact entry-path row from GitHub Traffic Popular content when available. This is a
rolling UTC observation, not a claim of exact 24-hour buckets. GitHub exposes only retained
popular-path rows; absence means `unobservable`, never zero or under ten. Compute qualified views
as `max(0, raw path views - manually logged owner previews)` only when the exact row is present.
Record only the URL and boundary-compliant disposition of any interest issue; do not duplicate
submitter content here.

Freeze the release copy and topics during the window unless a platform, privacy, security, or
misleading-claim concern requires immediate correction. At day 14, a retained exact-path row with
fewer than ten qualified views or zero qualifying self-reported interest signals means `GitHub-native
discovery: insufficient signal`. If the path is absent but interest is nonzero, the view result is
inconclusive rather than low. An insufficient result ends this channel; it does not justify
reposting or weakening the data boundary. A positive result still does not unlock checkout or
supersede the charter's 45-day/100-view and human-interest gate.

A qualifying self-reported signal follows the charter definition: one in-window public form issue
per non-owner, non-bot GitHub account, with the boundary acknowledgement and an in-scope generic
outcome. The account, identity, role, and intent are not authenticated. Duplicates, owner actions,
bots, reactions, and out-of-bound submissions count zero. The separate commissioning signal is
only the explicit nonbinding form option requesting a future private route to discuss the pilot;
it is not an order, promise to buy, or customer.

### Unsafe public-submission response

The issue form cannot enforce its warning. If prohibited or possibly sensitive content appears,
do not quote, summarize, hash, screenshot, or copy it into project files, comments, or logs. Keep
any public response minimal, advise the submitter to remove the content, stop counting or promoting
the channel, and escalate to the human owner for GitHub's private support or content-removal route.
